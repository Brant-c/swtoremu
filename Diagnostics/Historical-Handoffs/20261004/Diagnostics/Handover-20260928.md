## 16. Phase exit is incomplete — the destroy removes membership, not the UI

`phsPhaseInfo.OnReplicationNodeDestroy` (`phsPhaseInfoClassMethods.txt:70`) does
only four things:

1. removes `Me` from `node2.phsPhases` (membership),
2. `ClearPlayerJoinOverride` for each player,
3. `$PHASE.UpdateGatewayForInstance(...)`,
4. `call event Me:Replication_Destroy`.

It does **not** call `OnPhasedInstanceUpdated`. That method
(`phsoracleclassmethods.txt:170`) is the only code that clears the story-area UI
(`OnInstanceChanged` -> `UpdateGuiForPhase` -> banner), and its **sole caller** is
`phsParticipant.OnPlayerCharacterNodeReady` (`phsParticipantClassMethods.txt:2`),
which fires once at character creation. So destroying the `phsPhaseInfo` child can
remove membership but cannot clear the banner — matching the observed "no UI
indication of leaving the phase".

The exit trigger path is unrecovered: `phsGateway.TriggerLeave` is `// unknown`
(`phsGatewayClassMethods.txt:19`). Only `TriggerEnter` exists, and it handles
ENTRY (`OnPlayerEnteredGateway` -> join popups). `phsClassPhasedInstance.
OnPlayerEnteredGateway` for `phsCanExit` only calls `_HideJoinPopup`.

Conclusion: phase exit and room streaming are **one native area transition**, not
two independent script operations. The invisible wall and the missing exit UI are
the same missing native room/area streaming; the destroy is a necessary but not
sufficient piece.

`me` is bound by the class itself. The `me[id=0, invalid]` in run 1 was therefore
purely fallout from the wrong class hash, not a missing target argument — do not
add a target-node field.

## 19. POSTMORTEM — CrtApplyHook crashed the client on world load; REMOVED

The `AreaMessageDispatch` hook added in section 18 **crashed the client exactly
when it was going to load into the world**. It has been fully removed and the
hook rebuilt without it. Do not re-add it in this form.

### Root cause — wrong function signature, two defects

The hook was declared and forwarded as:

    typedef void (__thiscall * AreaMessageDispatch_t)(void* pThis, DWORD opcode);
    void __stdcall AreaMessageDispatch_Hook(void* pThis, DWORD opcode)

The real dispatcher at `0x0064ED70` takes **three** stack arguments, not one.
From `Diagnostics/swtor-disasm.txt` in the CRT branch:

    0064F0D1: lea eax,[ebp+0Ch] / push eax
    0064F0D5: mov edi,dword ptr [ebp+14h]     <-- 3rd argument, the reader
    0064F0DA: call 0097C4C0                   (reads stream id from it)
    0064F0E5: call 0097D2A0                   (deserializes the GomUpdate)

so the signature is at least `(this, arg2, reader)`. The AreaRequestRPC branch
(0x0064EDF5) also reads `[ebp+14h]`. Two concrete defects followed:

1. **Calling-convention mismatch.** The typedef was `__thiscall` but the hook was
   `__stdcall`, so the trampoline and the hook disagreed about who owned the
   `this` register and stack cleanup. This alone corrupts the frame.
2. **Truncated argument list.** Only `opcode` was declared and forwarded. The
   caller pushed a third argument (`[ebp+14h]`, the byte reader) which the hook
   then supplied as garbage/zero, and the forwarded call passed one register
   short. The dispatcher dereferences that reader during world load, hence the
   crash at exactly that moment.

A third, lesser issue: the dispatcher is reached through a vtable, so there is
no direct `call 0064ED70` site in the dump to confirm the full argument count.
The argument count should have been established from the disassembly *before*
writing the hook, not assumed from a one-argument guess.

### State now

- `ToR.cpp`: no `AreaMessageDispatch` / `CrtApplyHook` / `g_areaMessageCount`
  remain; install-summary line restored to `... write=%s"`.
- Rebuilt `Client/Hook/Bin/x86/MemoryMan.dll` (Release/Win32, 0 errors);
  symbol check confirms neither string is in the binary. 192 functions again
  (193 while the bad hook was present).
- The **safe** `ParseInboundFrame_Hook` streaming-opcode filter (CRT `0x0D446E80`,
  AwarenessEntered/Range, AreaRequestRPC, AreaHackPack) is retained and verified

  forwards unchanged.

### Rule for the next attempt

Re-derive the exact signature from `swtor-disasm.txt` first, and match the
codebase convention: every other `__thiscall` hook here uses
`void __fastcall X_Hook(void* pThis, void* EDX, ...)` with a matching
`__thiscall` typedef (e.g. `AreaRpcSend_Hook`). Reuse that pattern verbatim.
The lower-risk alternative is to hook the already-known concrete
`0x00977300`/`0x0097D2A0` reader calls, or to resolve the vtable consumer from
inside a correctly-signatured dispatcher hook.
